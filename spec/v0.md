# Scenario spec v0

Status: draft. Robotense publishes and maintains this standard. The text is published under CC BY 4.0, and the code and examples under Apache-2.0.

**Versions.** The current version is v0.4. v0.1, v0.2 and v0.3 are minor versions that add fields to the episode record (§8.1) and change no other record; v0.2 adds `simulated`, `simulator.physics_options_sha256` and the checker `molmospaces_pnp_port_v1` (§8.4); v0.3 adds `generator.seedless`, for a scene generator that draws no random number (§8.1). v0.4 changes only the trust entry (§7): its verdict follows the limits-of-agreement rule, so AGREE means that, under a normal model, about 95% of the assessed cells lie within the tolerance, and at least 74% for any distribution; it also adds the fields that let a validator recompute that verdict. Trust entries labelled v0 keep the v0 rule. Two clarifications made in v0.4 apply to every label (§14, Clarifications). Versioning rules, and how records of earlier versions are read, are in §14.

**Scope.** v0 does not define valid-goal sets for ambiguous instructions, timed bounds or multi-agent scenes.

**Lineage.** v0 builds on BDDL's declarative goal predicates ([BEHAVIOR](https://behavior.stanford.edu/), Srivastava et al., 2021). It adds STL-style robustness margins and LTLf-style ordering and "never" constraints. None of these constructs is new by itself.

## 1. Document

A scenario is one YAML document.

```yaml
spec_version: v0
id: <string, unique within a library>
task:
  instructions: [<string>, ...]        # paraphrase variants; factor instruction_variant indexes them
  embodiment: <string>                 # e.g. droid_franka, so101, yam_bimanual
  embodiment_profile: <profile ID>     # draft: robot profile for access, clearance and feasibility (spec/variance-v0.md §5.1)
scene:
  base: <scene reference>              # simulator-neutral asset ID or scene file, or a generated scene (below)
  objects: {<name>: <asset ID>, ...}   # names used in predicates
  reference_path: <path or null>       # draft: policy-independent anchor path (spec/variance-v0.md §5)
factors: [<factor>, ...]               # §2
goal: <goal or feasibility block>      # §3
feasibility: <rule or null>            # draft: rule that sets each instance's feasibility status
constraints: [<constraint>, ...]       # §4, may be empty
stages: [<stage>, ...]                 # §5
nominal_ref: <scenario id or "self">   # the factor values that define Δ = 0
real_reproducible: <block>             # §6
trust: [<trust entry>, ...]            # §7, filled by calibration, empty at authoring
```

The scenario hash is SHA-256 over the canonical JSON serialization of the document, excluding `trust`. Every episode record carries this hash. A scenario family produced by a generator from its factor values, with no stored document per instance (as in our failure-search pilot), is identified instead by the SHA-256 of the canonical JSON of the instance's parameters, which determine it (§2, purity).

**Draft additions.**
- **Generated scene reference.** `scene.base` may name a generated scene: `{generator: <name>, version: <v>, blueprint_hash: …, furnishing_hash: … | null, scene_hash: …}`, for example with `generator: homegen`, our home generator. A skill fixture names its fixture ID in place of the blueprint.
- **Embodiment profile and reference path.** Formats in `spec/variance-v0.md` §5 and §5.1.
- **Feasibility block.** `goal` may be a map from feasibility status to goal, `{feasible: <goal>, infeasible: <goal>, ambiguous: <goal>}`, with `feasibility` naming the rule that sets the status per instance. A plain goal applies to every status.

## 2. Factors (parameter block)

```yaml
- name: light_lux
  low: 100
  high: 1000
  nominal: 500
  kind: float            # float | int (inclusive bounds) | enum
  values: null           # list for kind: enum
  unit: lux
  failure_type: visual   # one of the taxonomy below
```

- **Failure types**: `instruction`, `visual`, `layout`, `object_identity`, `object_state`, `contact`, `long_horizon`, `safety_constraint`.
  - A factor carries `long_horizon` only when it changes the step count, for example the number of items to clear.
  - **Assigning a type.** A factor takes the type of the condition it is designed to vary. Among the types: `visual` covers lighting, background, blur and camera; `layout` covers placement, clutter and distractors; `object_identity` covers unseen objects; `contact` covers contact and dynamics, including friction. A factor that also changes something else keeps the type of its intended variable, and its design names the other changes as confounds of the attribution. Two bands on one factor share its type.
- **Purity.** A scenario is a pure function of its factor values. Any derived placement, such as a distractor ring, is computed from factors by a documented rule. A factor vector fully determines the initial scene, up to the simulator seed.
- **Unit-cube mapping.** Search works on [0,1]^d, with u clamped below 1. Each float factor maps linearly from low to high. An integer factor takes low + floor(u·(high − low + 1)), so every integer gets an equal share of the interval (the pilot's rule; rounding would give the two end values half shares). Enum factors take floor(u·|values|).
- **`policy_sensitive`** (optional, default true): false marks a factor the policy under test does not read, such as light colour temperature for a policy that reads no pixels. Such factors are negative controls: a failure attributed to one points to a confound.

## 3. Goal predicates and margins

**Grammar** (EBNF):

```
goal       := pred | "all" "(" goal {"," goal} ")" | "any" "(" goal {"," goal} ")"
            | "seq" "(" goal {"," goal} ")"
pred       := "inside" "(" obj "," obj ["," tol] ")"
            | "on" "(" obj "," obj ["," tol] ")"
            | "upright" "(" obj ["," angle] ")"
            | "gripper_released" "(" obj ")"
            | "joint_above" "(" obj "," joint "," number ")"
            | "not" pred
tol        := number            (metres)
angle      := number            (degrees)
```

**Semantics.** Each predicate p has a robustness margin ρ_p(s) over simulator state s, in metres or degrees. Its sign gives truth: ρ > 0 means true.

| Predicate | Margin ρ | Default tolerance |
|---|---|---|
| `inside(a, b, tol)` | tol − d(c_a, V_b), where c_a is a's centre and d is the distance from that centre to b's interior volume (0 if inside) | 0.07 m (the value RoboCasa's counter-and-stove pick-and-place checks pass as `th`, where it bounds the horizontal distance between object and container origins) |
| `on(a, b, tol)` | min(tol − horizontal distance from c_a to b's top-surface polygon, contact_gap_max − vertical gap) | tol 0.03 m, gap 0.01 m |
| `upright(a, angle)` | angle − tilt(a), where tilt is the angle between a's up axis and world up | 30° (the upright limit the Kaedim YAM harness uses when scoring its cup and bottle tasks; it uses 40° for stacked bowls) |
| `gripper_released(a)` | min over fingers of distance to a, minus 0.005 m | n/a |
| `joint_above(a, j, x)` | q_j − x | n/a |
| `not p` | −ρ_p | |

- `all` takes the min, and `any` takes the max.
- Mixed units are normalised before min or max. Each margin is divided by its predicate's tolerance scale (tol, angle, or a declared `scale`). Every margin is therefore dimensionless, and ±1 means "one tolerance away".
- **End-state goal.** A non-`seq` goal is evaluated at the final step T: ρ_goal = ρ(s_T).
- **Ordered steps** (first-time-true semantics). A step *becomes true* at time t when it is true at t and false at t − 1 (or t = 0). In `seq(g1, …, gn)`, t1 is the first time g1 is true, and for i > 1, ti is the first time at or after t_{i−1} at which gi becomes true. A step that was already true before t_{i−1} and stayed true does not become true again, so it does not count. `seq` holds if every ti exists and gn still holds at T. `seq` appears only as the whole top-level goal; a `seq` inside `all`, `any`, `not`, another `seq`, a stage or a constraint is refused (the parser in `spec/rubric.py` raises `CompileError`).
- **Ordered-step margins** (window rule). Step i's *window* runs from ti to t_{i+1}, or to T when t_{i+1} does not exist. A step with a time, other than the last, has margin max over its window of ρ_gi: how far into gi the episode went while gi was the current step. The last step, when it has a time, has margin ρ_gn(s_T), as an end-state goal. The first step without a time has a margin ≤ 0: if gi was true at t_{i−1} (out of order), −ρ_gi(s_{t_{i−1}}); otherwise the largest ρ_gi over [t_{i−1}, T]. ρ_seq is the min of the margins up to and including the first step without a time. *Sign.* ρ_seq > 0 exactly when `seq` holds: on success every window contains ti, where ρ_gi > 0, so every step margin is positive, and ρ_gn(s_T) > 0 by definition; on failure the min includes a step margin ≤ 0 (an untimed step's, or ρ_gn(s_T) ≤ 0 when gn is false at T). *Scale.* A margin taken at each step's first-true moment, where ρ_gi has just crossed 0, would score a success at about (slope of ρ_gi) × control_dt whatever the depth reached; the window margin is the depth reached, so it does not shrink with control_dt. *Limits.* Like any margin built on first-time-true events, ρ_seq is a signed depth, not a guaranteed perturbation radius: a trace change smaller than |ρ_seq| can move an event time, for example make g_{i+1} true just before ti, and so change the verdict. A step may lapse after its window without entering the margin, as the semantics allows. When t_{i+1} = ti the window is one moment and step i's margin is ρ_gi(s_ti). Implementation is one forward pass that tracks the current step and its window maximum. The reference evaluator on margin traces is `seq_holds` in `spec/rubric.py`; it returns ρ_seq and each step's margin.
- **First failed predicate.** For a failed episode, report the first step i that never became true at or after t_{i−1}. Report the leaf predicate of gi with the smallest margin at the time of its best margin, and that timestamp. For an out-of-order step, report t_{i−1}.

**Proposed predicates.** These names are reserved. They are outside the grammar above, and the parser in `spec/rubric.py` refuses them. Each enters the grammar, with its definition, in the version whose checker implements it:
- `base_stalled`, `any_tipped`, defined in `spec/variance-v0.md` §9;
- `opened`, `grasping`, `close_to`, `collides`, `wedged`, `limit_force_above`, `reported_unable`, names proposed for skill-fixture checkers and not defined in v0.

## 4. Constraints ("never")

```yaml
constraints:
  - id: no_drop_glass
    never: "not on(glass, table, 0.05)"     # any predicate expression
    after: start                           # start | stage:<id>
    failure_type: safety_constraint
```

- **Semantics.** The constraint is violated if its expression is true at any step after `after`. Its margin is ρ_c = min over t of −ρ_expr(s_t). A constraint that was never close to violation has a large positive margin.
- **Episode margin.** ρ_episode = min(ρ_goal, min over c of ρ_c). Success requires ρ_episode > 0. A goal-met episode that violated a constraint is a **constraint failure**, recorded separately from goal failures.

## 5. Stages and stage classes

Stages give partial credit and failure location. Each failed episode gets a stage class: G (acquire), T (transport) or P (place); S marks a success, or a failure the stages do not locate.

```yaml
stages:
  - {id: acquire,   holds: "lifted(mug, 0.03)",          class_if_last_failed: G}
  - {id: transport, holds: "inside(mug, bowl, 0.07)",    class_if_last_failed: T}
  - {id: finish,    holds: "all(inside(mug, bowl, 0.07), upright(mug, 30), gripper_released(mug))", class_if_last_failed: P}
```

- `lifted(a, h)` is a derived predicate: max over t of (z_a(t) − z_a(0)) − h, while a is in contact with both fingers. It is an event, so it is evaluated over the whole history.
- `stage_reached` is the last stage whose `holds` was true at any time, in order.
- `stage_class` is S if the goal holds at the end. Otherwise it is the `class_if_last_failed` of the first stage not reached. When every stage is reached and the goal still fails (for example a wrong-order `seq`, Example 2), `stage_class` is S: the failure lies outside the stages and is located by the first failed predicate (§3).
- A checker that is not compiled from this grammar maps its own stages to the classes and documents the map. The pilot's six stages map as: approach, grasp, lift → G; transport, place → T; release → P; the placement reached → S, including when a distractor was disturbed, which is then a constraint failure with the goal met (§4). The pick-and-place checker `molmospaces_pnp_port_v1` maps touch, lift → G; support → T; finish → P (§8.4). **Episode-record rule (v0.2):** in a v0.2 episode record, `stage_reached: "none"` means that no stage was reached, and it means nothing else; a checker with a stage whose id is `none` cannot write v0.2 records until it renames that stage. `spec/checker.py` returns null when no stage is reached, and an exporter writes `"none"`. The validator enforces the value for `molmospaces_pnp_port_v1` (§8.4); for other checkers it does not know the stage ids, and review checks the rule.
- For a multi-object task, stages are declared per object (`for_each: [cube, mug, ...]`), and the episode record carries one stage class per object unit.
- **Skill tag (draft).** A stage may carry `skill: <skill ID>` (for example `open_drawer`). A task that fails at a tagged stage is traced to the skill fixture with that ID.

## 6. Real-reproducibility block

```yaml
real_reproducible:
  objects: {mug: "YCB 025_mug", bowl: "IKEA 365+ bowl 16cm"}   # purchasable set or measured asset
  frame: robot_base                                             # all placements in this frame
  placements_from_factors: true                                 # obj_x, obj_y, obj_yaw map 1:1 to the real layout
  lighting: {unit: lux, measured_at: workspace_centre}
  camera: {extrinsics_from: calibration_file_id, exposure: locked, white_balance: locked,
           image_stats: {mean_luma: null, luma_std: null}}   # 2611.13810: auto-exposure likely absorbed an 11.5x illuminance drop
  record_initial_poses: true                                    # ArmnetBench omitted them; needed for episode pairing
  tolerance_note: "placements reproducible to ±1 cm, ±5°"
```

A scenario without this block can be searched but cannot be trust-tagged. The measured camera, arm and scene data of a twin of a real setup, with their checks, are in the twin calibration record (§13).

**Verdict rule (v0.4): limits of agreement.** δ is `tolerance`. A cell's difference is its simulated rate minus its real rate; bias and scatter are the mean and the standard deviation, net of trial noise, of the differences over the assessed cells.

- **What AGREE claims.** The 95% limits of agreement of the differences over the assessed cells lie inside ±δ, where LoA = |bias| + 1.96 × scatter is the larger in absolute value of the two limits bias ± 1.96 × scatter of Bland and Altman (1986, §12.5), with the scatter net of trial noise. Under a normal model, about 95% of these cells are then within ±δ of the real rate; for any distribution, at least 74% are (Chebyshev's inequality: at most 1/1.96² lie outside). AGREE is given only when an upper confidence bound on LoA, at a level of at least 95%, is at most δ, so a false AGREE has probability at most 0.05 at the boundary, given the nominal 95% coverage of the bias and scatter intervals. The claim covers these cells only, and δ is a tolerance on the rate difference of a single cell.
- **Method `union_bound`.** From the bias interval [b_lo, b_hi] (`bias.ci95`) and the scatter interval [s_lo, s_hi] (`scatter_net.ci95`), both at 95%: U = max(|b_lo|, |b_hi|) + 1.96 s_hi, an upper bound on LoA, and L = dist(0, [b_lo, b_hi]) + 1.96 s_lo, a lower bound (dist is 0 when the interval contains 0). A bound misses only when one of the two intervals misses on one side, so each holds at a level of at least 95% when each interval misses each side with probability at most 2.5% (union bound over two one-sided misses). U over the non-FLOOR cells is computed in the same way from `non_floor`.

The rule, in order:
- `floor`: every validated cell of the KPI is labelled FLOOR (§12.1), so `non_floor.n_cells` is 0.
- `agree`: U ≤ δ, and the padding check passes: `non_floor.n_cells` is at least 2 and U over the non-FLOOR cells is at most δ. An entry with U ≤ δ that fails the padding check is `inconclusive`.
- DISAGREE: L > δ. The padding check does not apply. The cause:
  - `disagree_offset_and_scatter`: 1.96 s_lo > δ and the bias interval lies entirely outside ±δ.
  - `disagree_scatter`: 1.96 s_lo > δ and the bias interval does not lie entirely outside ±δ. Removing the offset cannot meet the tolerance.
  - `disagree_offset`: 1.96 s_hi ≤ δ. Removing the offset would meet the tolerance, so the offset is correctable; the corrected predictions still need cells that were not used to estimate the offset.
  - `disagree_unresolved`: none of the above. The data show disagreement but cannot say whether the offset alone explains it.
- `inconclusive`: otherwise.
- `not_yet_calibrated`: no real outcomes for the entry's scope in the validation domain, or an uncalibrated twin under a customer plan (§13.3).

**The padding check.** A FLOOR cell (both sides at 0 or both at n, say) has a difference near zero. It pulls the bias toward zero and shrinks the scatter, so adding tasks that every policy fails, or every policy passes, could carry an entry to AGREE. The check makes AGREE hold on the cells that carry information. FLOOR cells push toward agreement, so leaving them in makes DISAGREE harder to reach, and the check is needed for AGREE only.

**Demonstrated tolerances.** For an entry that is not `floor` and has its scatter intervals, AGREE holds exactly when δ_A ≤ δ, and DISAGREE exactly when δ_D > δ (a null δ_A never gives AGREE, and a null δ_D never gives DISAGREE). A reader with another tolerance reads the verdict off them, and a tolerance chosen after the data stays visible. δ_A reads on its own: "with at least 95% confidence, the limits of agreement over these cells lie within ±δ_A". A value above 1 means that no tolerance on the rate scale would give AGREE.

**Not determined (v0.4).** When `scatter_net.ci95` is null (an input without an interval method), the verdict is the one the rule gives for every scatter interval that contains the scatter point `scatter_net.value`. When such intervals give different verdicts, the entry is `not_determined` and `verdict_possible` lists all of them. `non_floor.scatter_net.ci95` is treated in the same way in the padding check. With s the scatter point, L_s = dist(0, [b_lo, b_hi]) + 1.96 s and U_s = max(|b_lo|, |b_hi|) + 1.96 s:
- U_s ≤ δ: `agree` or `inconclusive`, or only `inconclusive` when the padding check cannot pass.
- L_s ≤ δ < U_s: `inconclusive`.
- L_s > δ: AGREE is excluded. The possible causes follow from the cause rules with s_lo ≤ s ≤ s_hi, and `inconclusive` stays possible when dist(0, [b_lo, b_hi]) ≤ δ. For example, a bias interval outside ±δ with 1.96 s ≤ δ leaves `disagree_offset` or `disagree_unresolved`; with 1.96 s > δ it leaves `disagree_offset_and_scatter` or `disagree_unresolved`.

`spec/validate.py` computes the list exactly: the rule compares s_lo and s_hi only with fixed cut points, so it evaluates one interval in each region between them. δ_A and δ_D are null while an interval they need is null.

**Bias and scatter.** They are separate inputs because a simulator's stable offset can be corrected and cell-specific scatter cannot. They follow the two aspects that NASA-STD-7009B, Appendix E.3.4, names for a validation comparison: the difference between the means and the spread. Our scatter is the spread of the sim−real difference across the assessed cells, not the uncertainty around each result. E.3.4 sets no acceptance rule that combines the two: it states that a favorable comparison requires, at a minimum, some overlap between the uncertainty intervals around the means, and 7009B asks that acceptance criteria be recorded. The limits of agreement are one way to combine them, and they make δ a tolerance on the rate difference of each cell (§12.5).

**Verdict rule of v0 entries.** Kept for records labelled v0 (§14), which carry no v0.4 field and never `disagree_unresolved`. The bias interval is `bias.ci95` and the scatter interval is `scatter_net.ci95`.
- An offset is a bias interval entirely outside ±δ; wide scatter is a scatter interval whose lower bound exceeds δ. `disagree_offset_and_scatter`: both. `disagree_offset`: an offset only. `disagree_scatter`: wide scatter only.
- `agree`: neither, the bias interval lies inside ±δ, and the upper bound of the scatter interval is at most δ. This tests bias and scatter separately; it does not say that the cells agree within δ (§14).
- `inconclusive`: otherwise.
- `floor` and `not_yet_calibrated`: as in v0.4.
- When the scatter interval is null, the scatter point `scatter_net.value` stands in for it: an offset with scatter at most δ gives `disagree_offset`; no offset, scatter at most δ and a bias interval not inside ±δ gives `inconclusive`; every other case gives `not_determined`. Its `verdict_possible`: `disagree_offset_and_scatter`, `disagree_offset` when the bias interval lies outside ±δ and scatter exceeds δ; `disagree_scatter`, `inconclusive` when scatter exceeds δ without an offset; `agree`, `inconclusive` when scatter does not exceed δ and the bias interval lies inside ±δ.

**Rules for every label.**
- **`not_yet_calibrated`** entries have `n_cells` and `n_real_episodes` 0, and `tolerance`, `fitted` and every estimate null. Any other verdict needs `plan_sha256`, `kpi`, `tolerance`, `bias.ci95`, `scatter_net.value` and at least one cell.
- **Aggregate entries:** only for a plan KPI with `statistic: rate_difference`; a rank KPI carries no trust entry and no §7 verdict; it keeps the plan's rank verdict. The report rules for aggregate verdicts are in §12.4, item 4.
- `referent.dataset_ids` must point to real outcomes. Synthetic paired data may test an estimator; it never populates a trust entry.
- `simulator_tier` stays beside `simulator`: the tier alone cannot identify a release.

- **Identity and replay (v0.1).** A v0.1 record says which checker release scored it (`outcome.checker`, `checker_version`), which generator release built its scene from which constraints and seeds (`generator`, `scene_seeds`), and on which device and settings the policy ran (`compute`). Seeds alone do not identify a replay. NVIDIA states that cuBLAS results are bit-wise reproducible only on the same architecture, the same number of SMs and the same toolkit version ([cuBLAS, Results reproducibility](https://docs.nvidia.com/cuda/cublas/index.html), fetched 2026-11-25), and PyTorch that results may differ between CPU and GPU with identical seeds ([Reproducibility](https://docs.pytorch.org/docs/2.15/notes/randomness.html), fetched 2026-11-25). A record therefore claims replay only on its own `compute` block and its own renderer (`simulator.renderer`); a replay on other hardware is a new trial, compared by outcome, not by trace.
- **What the replay fields do not say.** `events` and `fork` record what happened in a trial so that it can be rebuilt. They say nothing about how events were chosen or whether forking finds failures faster; the scenario document has no `events` block in v0.1.
- `perturbed` supports attribution: single-factor perturbations attribute a failure to one type; multi-factor episodes carry the set, and a hierarchical model handles them.
- **Per-cell failure-mix block** (written by analysis, not per episode): unit counts by stage class, sim and real; TVD with a trial-bootstrap 95% CI; permutation p.
- **Skill-fixture draft fields**: `feasibility` (status, rule, inputs), `policy_report` (the policy's reports, with times), and `outcome.class` (`success`, `handled`, `false_refusal`, `incomplete` or `unsafe`). They are drafts outside the table above, so a v0, v0.1, v0.2 or v0.3 record carries them only under `x.<producer>`.

### 8.2 Reconciliation with the pilot

Our failure-search pilot keeps its own record format and exports each trial as an episode record. The export follows these rules:
- The pilot generates each scenario from its factor values and stores no document, so `scenario_hash` and `nominal_ref` are full SHA-256 hashes of instance parameters (§1). Its nominal reference is the same layout with every other factor at nominal, so layout positions are never in `perturbed`.
- Its checker keeps its own definitions, named `failsearch_v0` in `outcome.checker`: `goal_margin` is null, and `episode_margin` is positive exactly on success, guides search and is not a robustness margin (§8.1). Its tolerances (for example a 25° tilt and a 5 cm lift) are its checker's, not the §3 defaults, which apply to grammar scenarios.
- Its six stages map to stage classes as stated in §5. A distractor displaced by more than 5 cm is a constraint failure with the goal met, with margin `distractors_undisturbed` = (0.05 − largest displacement)/0.05, the §4 normalisation.
- Its scripted policy has `policy.family` `scripted` and `checkpoint_sha256` null, since it has no weights.
- Its scene builder draws no random number: each scene, distractor placements included, is a function of the factor values. Its v0.3 export names its generator by the pilot's package name and release, with `constraints_sha256` null, `seeds` `{}` and `seedless` true, and with `scene_seeds` null, because a point of the search stream, not a seed list, draws each scenario. It has no constraints document. It writes no v0.1 or v0.2 records: no `generator` value of those versions describes a seedless generator, and null would claim a stored document.
- Fields of its own go under `x.failsearch`.
- Its objects are primitives with no purchasable or measured counterpart, so under §6 its scenarios cannot be trust-tagged.

### 8.3 Open items

1. **A generator that draws no seed.** Closed in v0.3 (2026-11-26). A generated family whose scene is a deterministic function of its factors, such as our failure-search pilot, fitted neither v0.1 value: `generator.seeds` needs at least one base-scene seed, and a null `generator` means a stored scenario document. Ruling: v0.3 adds `generator.seedless` (§8.1); with it true, `seeds` is empty. Null keeps its meaning in every version. v0.1 and v0.2 are unchanged, so such a generator has no `generator` value under those labels, and its producer exports v0 or v0.3. An empty map without the flag was rejected because a reader could not tell it from seeds left out by mistake.
2. **One trace hash per record.** A v0.1 record carries one trace hash, for its own device (§8.1, identity and replay), so a reader without that device cannot check a replay. Proposed: a trace hash per device, including a CPU reference.

### 8.4 Checker `molmospaces_pnp_port_v1` (from v0.2)

Status: **draft.** The definitions behind `outcome.checker: molmospaces_pnp_port_v1`: MolmoSpaces' pick-and-place success rule (`PnPChecker`, MolmoSpaces at commit `cd23bece`) as ported into our evaluation harness, with the stages, terminal classes, first failed predicate and margin below, which are ours. `outcome.checker_version` is the harness's release at the record's code commit. A release that changes any rule of this section takes a new checker name or version, stated here.

**Per step.** One policy step is 33 physics substeps of 2 ms (0.066 s); step k (0-based) ends at (k + 1) × 0.066 s from the first observation, and the last step T is the 606th. After each step the checker gives `robot_contact` (the pickup touches any body of the robot's tree, gripper or arm), `supported` (the receptacle carries at least half the pickup's weight through contact forces within 30° of vertical, or their fallback heuristic holds), `carried` (their carry-forward: not supported, but the pickup's pose relative to the receptacle within 5 mm and 10° of a pose cached on a supported step), and the receptacle's displacement and tilt from its start pose. The pickup's height is its body origin's z; z₀ is that height at the first observation, after the settle.

**Success** (their rule): at step T, (`supported` or `carried`), not `robot_contact`, receptacle displacement at most the episode's own limit and tilt at most its own limit (the DroidMini values 0.05 m and 15° when the episode carries them; otherwise their task config's 0.1 m and 45°).

**Stages.** Each stage is reached at the first step at or after the previous stage's step at which it holds (§5, the reference checker's in-order rule):

| Stage | Holds at step k | Class when it is the first stage not reached |
|---|---|---|
| `touch` | `robot_contact` | G |
| `lift` | z_k − z₀ > 0.03 m and `robot_contact`, with z_k and z₀ at full float64 precision as the simulator reports them | G |
| `support` | `supported` (carry-forward does not count) | T |
| `finish` | success; evaluated at k = T only | P |

- `stage_reached` is the last stage reached, or `"none"`; `stage_times` lists exactly the stages reached. The lift comparison uses full-precision heights at run time. Our harness's step log rounds the height to 10⁻⁵ m, so an exporter does not recompute `lift` from the log; it takes the stage from the checker's run-time result.
- `stage_class` is S on success. Otherwise it is the class of the first stage not reached. Because `finish` holds only at T and equals success, a failure never reaches it, and the §5 case of every stage reached with the goal failing does not arise.
- **Push-ins.** A success without `lift` reached (the pickup pushed or tipped into the receptacle) is a success with class S under their rule, and its `stage_reached` is `touch` (or `"none"` when the robot never touched it). A `"none"` success counts as a push-in: it is a success without a lift, and the evidence report's push-in count includes it. The record marks every push-in under the producer's own field (`x.<producer>.push_in`); it is not an outcome field.
- **Stage reached on a success.** A success can end at `finish` (the usual path), `touch` (push-in), `lift` (success through carry-forward when every supported step came before the lift) or `"none"` (the pickup reached the receptacle with no robot contact). It never ends at `support`: a success with support reached also reaches `finish` at T. The validator refuses `support` on a success and requires `stage_times` to list exactly the stages reached, in non-decreasing time, on successes and failures alike.

**Terminal classes** (failures only; null on success). Each is a function of the stage reached and the state at T, so exactly one applies to every failure, and the earliest-event rule of §8.1 (`pulled_off` against `drop`) has nothing to decide:

| Terminal class | Stage reached | `first_failed` stage, predicate and t |
|---|---|---|
| `no_contact` | `"none"` | `touch`, `robot_contact`, end of step T |
| `not_lifted` | `touch` | `lift`, `lifted_3cm`, end of step T |
| `lost_after_lift` | `lift` (never supported at or after the lift) | `support`, `supported`, end of step T |
| `left_support` | `support`; at T neither supported nor carried | `finish`, `supported_or_carried`, the first step of the final run of steps with neither |
| `goal_not_held` | `support`; at T supported or carried, but the pickup is touched, or the receptacle moved or tilted beyond its limit | `finish`, the first failing of `no_robot_contact`, `receptacle_pos_disp`, `receptacle_tilt` in that order (the port's order), the first step of the final run in which that term fails |

These classes say where the episode stopped progressing. They are not the event classes of other checkers and do not reuse their names: `lost_after_lift` needs no grip-break event and includes a pickup still held in the air at T, so it is not the `drop` of `worktop_v0`; `not_lifted` includes a pickup pushed or pulled off the counter, which this checker does not separate, so `knocked` and `pulled_off` are not used. Separating them needs an off-surface test on the pickup and a new checker version.

**Margin.** `episode_margin` is 1 on success; on failure it is −(4 − r)/4, where r is the number of stages reached (0 to 3): −1, −0.75, −0.5 or −0.25. It is stage progress, positive exactly on success, for guiding search; it is not a robustness margin. `goal_margin` is null. `margin_components` may hold the terms at T. `constraint_margins` is empty: their rule folds the receptacle limits into success, so they are goal terms, not §4 constraints.

**Differences from the §3–§5 grammar**, for a reader comparing with `spec_v0_grammar` records: `lift` needs contact with the robot, not with both fingers, and measures the body origin; `support` is a contact-force test, not `inside` or `on`; the pickup has no `upright` term; the receptacle's displacement and tilt are goal terms.

**Validation.** `spec/validate.py` checks, for this checker, the stage reached against the stage class, the terminal class, the first failed stage and predicate, and the margin; on successes and failures, the keys of `stage_times` (exactly the stages reached) and their order (non-decreasing), no `support` on a success, a null `goal_margin` and empty `constraint_margins` (self-test faults "pnp …").

## 10. Worked examples

**Example 1: mug in bowl (pilot task, layout and contact factors).**

```yaml
spec_version: v0
id: kitchen_mug_in_bowl_001
task: {instructions: ["put the mug in the bowl", "place the mug into the bowl"], embodiment: droid_franka}
scene: {base: tabletop_kitchen_a, objects: {mug: ycb_025_mug, bowl: bowl_16cm, table: table_a}}
factors:
  - {name: obj_x, low: 0.38, high: 0.62, nominal: 0.50, unit: m, failure_type: layout}
  - {name: friction_scale, low: 0.7, high: 1.3, nominal: 1.0, failure_type: contact}
  - {name: light_lux, low: 100, high: 1000, nominal: 500, unit: lux, failure_type: visual}
  - {name: instruction_variant, low: 0, high: 1, nominal: 0, kind: int, failure_type: instruction}
goal: "all(inside(mug, bowl, 0.07), upright(mug, 30), gripper_released(mug))"
constraints: []
stages:
  - {id: acquire, holds: "lifted(mug, 0.03)", class_if_last_failed: G}
  - {id: transport, holds: "inside(mug, bowl, 0.07)", class_if_last_failed: T}
  - {id: finish, holds: "all(inside(mug, bowl, 0.07), upright(mug, 30), gripper_released(mug))", class_if_last_failed: P}
nominal_ref: self
real_reproducible: {objects: {mug: "YCB 025_mug"}, frame: robot_base, placements_from_factors: true, lighting: {unit: lux, measured_at: workspace_centre}}
trust: []
```

An episode where the mug is lifted, carried, and dropped 9 cm from the bowl rim gives:
- inside margin = (0.07 − 0.09)/0.07 = −0.29,
- stage_reached = acquire,
- stage_class = T,
- first_failed = transport.

**Example 2: clear two items in order (ordered steps, per-object units).**

```yaml
id: clear_table_ordered_002
goal: "seq(inside(plate, box, 0.05), inside(cube, box, 0.05))"
stages:
  - {for_each: [plate, cube], id: acquire, holds: "lifted($o, 0.03)", class_if_last_failed: G}
  - {for_each: [plate, cube], id: place, holds: "inside($o, box, 0.05)", class_if_last_failed: T}
```

If the cube enters the box before the plate, both objects are inside at T, but `seq` fails: the cube was already inside at t1 and never becomes inside after it (§3, first-time-true steps). The episode is a wrong-order failure: success = false, both object units have stage_class S, and first_failed points to step 2, at t1.

**Example 3: put the glass on the tray without knocking the bottle over (never constraint).**

```yaml
id: tray_glass_never_tip_003
goal: "all(on(glass, tray, 0.03), upright(glass, 20), gripper_released(glass))"
constraints:
  - {id: bottle_stays_upright, never: "not upright(bottle, 45)", after: start, failure_type: safety_constraint}
factors:
  - {name: bottle_gap, low: 0.02, high: 0.15, nominal: 0.10, unit: m, failure_type: layout}
```

An episode that places the glass correctly (goal margin +0.4) but tips the bottle to 60° gives:
- constraint margin = (45 − 60)/45 = −0.33,
- episode margin = −0.33,
- success = false, recorded as a constraint failure with goal met.

This is a goal-met violation. Search over `bottle_gap` looks for the gap at which such violations begin.

## 11. Benchmark records: reference sets and entry cards

Status: **draft.**

A simulator agreement benchmark scores **entries** (simulators, twins, world models, real-data baselines, a real-against-real ceiling) on how well their outputs predict released real outcomes, one **track** per reference set. It needs two records:
- a **reference set**: the real side of a track, frozen before any entry on it is scored;
- an **entry card**: one entry on one track, frozen before the track is scored.

Both are JSON documents carrying `record`, `spec_version` and `synthetic`, like the `cell_agreement` record (§12.1). A record's hash is the SHA-256 of its canonical JSON: keys sorted, no whitespace, UTF-8 without escaping (the `canonical` function of `spec/validate.py`). `null` means not stated by the source, and the record says so in prose where it matters. Unknown fields are an error.

**Validation.** `spec/validate.py` (standard library) checks field names and types, the allowed values, the rules between fields within a record (id form, classes and metrics, per-task maps, cells, budget keys, checkpoints per policy, a rule for declared-blind entries, `synthetic` false on reference sets), the entry card's reference-set hash and twin calibration link (§13.3), and the SHA-256 of `matching_file` and `information_used.rule`. It does not check licence rows against the benchmark's licence register, freeze conditions, the truth of prose fields, or whether `provenance` matches how the outputs were made; review covers those. `python3 -I spec/validate.py` runs it on `spec/examples/` and then applies known faults to the examples, failing unless each is rejected.

**Examples.** Track R2 of the benchmark (bimanual YAM, arXiv 2610.00731v2): `spec/examples/sim-agreement-r2-reference-set.json`, and the card of its published Kaedim authored entry, `spec/examples/sim-agreement-r2-entry-kaedim-authored.json`. Both are drafts: neither is frozen, and the entry card records what the paper and the released run files state, with gaps as `null`.

## 12. Credibility assessment records: cell agreement, assessment plan, calibration manifest

Status: **draft.**

An assessment has one **assessment plan**, fixed before counted data, which names a **calibration manifest** and is cited by every **trust entry** (§7) it produces; each cell of the comparison is a **cell agreement** record. All four are JSON records with `record`, `spec_version` and `synthetic`, hashed as in §11 (canonical JSON). `null` means not stated by the source; unknown fields are an error.

**Validation.** `spec/validate.py` checks field names, types and allowed values; the rules within each record listed below; and the links: a cell agreement record's plan (by `assessment_id`), KPI, policy, task, embodiment and calibration flag; a plan's calibration manifest and twin calibration record (each by hash), with the same simulator and embodiment; a trust entry's plan (by hash), with the same simulator, embodiment, pairing, independence and KPI, its cell counts, its calibration overlap, and its twin calibration status with the §13.3 rule for customer plans; and the SHA-256 of `source_document`. It also checks each trust entry's verdict, and `verdict_possible`, against the verdict rule of the entry's label (§7) on the entry's own values: for v0.4, the bias and scatter intervals over all cells and over the non-FLOOR cells, and the tolerance, with `delta_agree` and `delta_disagree` against the bounds they state; for v0, the bias interval (`bias.ci95`), scatter and tolerance. FLOOR is checked against the cell labels, and for v0.4 `non_floor.n_cells` against the count of cells not labelled FLOOR. It checks that an aggregate entry's KPI is a `rate_difference`. It does not recompute statistics from counts beyond d for `rate_difference` KPIs, nor the cell labels or prose; our report generator recomputes those, and review covers the rest.

**Examples.** The WidowX illustration compares SIMPLER's WidowX scenes, as run for the AutoEval paper's Table 3, with that paper's human-run real table (Table 2), using only the published counts ([Zhou et al., 2025](https://arxiv.org/abs/2503.24278v2)). The source states no SIMPLER version. All records have `status: illustration`:
- `spec/examples/ca-widowx-plan.json`: the plan, fixed after the data were seen, so `fixed_before_data` is false and every verdict reads "under the plan's rule, not pre-registered";
- `spec/examples/ca-widowx-calibration-manifest.json`: calibration history not disclosed, so the entries carry `calibration_overlap: "unknown"`;
- `spec/examples/ca-widowx-cell-agreement.jsonl`: 24 cell records, one per policy and task;
- `spec/examples/ca-widowx-trust-entries.jsonl`: an aggregate success-level entry with a verdict, and a `not_yet_calibrated` entry for `contact`. Both are labelled v0 and follow the v0 rule; the graded entry is `disagree_scatter` under the v0.4 rule too (§14, Validation).

The graded entry links no twin calibration record, so it is `uncalibrated` (§13.3), and its verdict is shown under the marks above to illustrate the record. It is an aggregate verdict over these 24 cells (§12.4, item 4) and says nothing about a failure type or stage, other SIMPLER scenes or other policies. Our analysis of the same counts, with intervals, is at [robotense.com/research/simpler-widowx-agreement](https://robotense.com/research/simpler-widowx-agreement/).

### 12.4 Design notes

Design notes on the records of §7 and §12: the choices behind their fields.
1. **`simulator` is nested everywhere:** `{name, version, config_hash}` in the plan subject, the manifest and the trust entry.
2. **Grader and termination are the §11.3 blocks**, for the real side in `referent` and for the simulated side in `subject.termination_rule`.
3. **The plan cannot hold its own hash.** `plan_sha256` is computed over the plan record. A document the plan was written from is pinned by `source_document.sha256`.
4. **Trust entry scope.** An entry has `scope` and `target`, and KPIs use the same `kind` and `target`, so type, stage and aggregate entries share one record. An aggregate KPI may carry the §7 verdict only when all three conditions hold: (1) it is a per-cell rate difference (`statistic: rate_difference`); (2) its tolerance was declared before counted data and justified against the intended use, or else the verdict carries the "under the plan's rule, not pre-registered" mark; (3) the verdict is labelled aggregate, shown after the type and stage rows, graded "context, not graded", and never quoted as agreement for a failure type or stage. A rank KPI carries no trust entry and no §7 verdict; it keeps the plan's rank verdict. The validator enforces condition 1; the plan's `fixed_before_data` records condition 2; condition 3 is a report rule.
5. **Verdicts.** `disagree_offset_and_scatter` covers an offset and scatter together. `disagree_unresolved` (from v0.4) covers a DISAGREE whose cause the data cannot resolve, so a DISAGREE is labelled offset or scatter only when the data show that cause. `not_determined` with `verdict_possible` covers a scatter interval without a method (§7).
6. **`calibration_overlap`** is `false` or `"unknown"`, not a bool. `false` means the calibration history is disclosed: the overlapping cells are marked `in_calibration` and excluded before the entry is fitted, so no entry ever holds overlapping cells. `"unknown"` means the history is not disclosed; the entry still carries a verdict, marked "calibration overlap unknown".
7. **No `data_provenance` field** in the trust entry: `referent.dataset_ids` holds the data.
8. **Plan subject.** The robot is `embodiment`; `policies` and `tasks` are listed so cell records can be checked against the plan.
9. **Linking fields.** Trust entry: `assessment_id` and `kpi` (which plan and KPI produced the verdict). Plan: `fixed_before_data` and `fixed_note` (they set the "not pre-registered" mark), `referent.real_repeat`, `subject.note` and `source_document`.

## 13. Twin calibration record

Status: **draft.**

A twin is a simulation of one physical setup: a specific robot arm, its control stack, its cameras and its scene. The twin calibration record lists the data measured on that setup and the checks that show the twin reproduces it, each with a tolerance. A sim-versus-real number made with a twin is a comparison result only when the twin's record has status `calibrated` (§13.3).

**Why.** A twin built from released data alone has to estimate every quantity the data do not record: joint calibration, control settings, camera poses and scene geometry. Our reasoning: on a hobby arm with unknown joint offsets, offsets and camera pose fitted from the same images can trade off against each other, so two fits can match the images equally well and place the gripper differently. Every published sim-versus-real comparison we read had the physical robot or scene, and we found no paired dataset that ships arm calibration files.

**Standards.** We found no ISO, ASTM or NIST document that defines how to calibrate or validate a robot twin for outcome comparison. ISO 9283 tests the physical robot, and a NIST project page states that "the fidelity of such virtual environments has not been studied in-depth" ([NIST, Digital Twins and Emerging Technologies for SME Workcells](https://www.nist.gov/programs-projects/digital-twins-and-emerging-technologies-sme-workcells), page updated 2026-04-23, fetched 2026-11-24). IEEE standards were not searched in depth. The record is our own.

**Not the calibration manifest.** The calibration manifest (§12.3) discloses which data and cells were used to tune a simulator, so validation can exclude them. This record holds the physical measurements of the setup. A twin can have both.

The record is a JSON document with `record`, `spec_version` and `synthetic`, hashed as in §11 (canonical JSON); `null` means not stated, and unknown fields are an error. Poses are in the robot base frame unless a camera's `mount` names another frame. Lengths are in metres, errors in millimetres, angles in degrees.

**Validation.** `spec/validate.py` checks field names and types; that per-joint maps and reference poses use the joint names, ids are distinct, drift keys are recording sessions, and quaternions have unit length; that `status` equals the §13.3 rule's result; and the links from entry cards, plans and trust entries (§13.3). It does not fetch the artefacts or check their hashes, nor the truth of the measurements; review covers those. `twin_gaps` in the validator lists what keeps a record from `calibrated`, for reports.

### 13.3 Status and the comparison rule

- **Status.** A record is `calibrated` exactly when every item has source `operator` or `us` and a `method`, `robot_unit` is given, every value §13.1 requires is present, every check is within its §13.2 tolerance, and `synthetic` is false. Otherwise it is `uncalibrated`.
- **Comparisons.** A sim-versus-real comparison here is an entry card of kind `simulator` (§11.2), or an assessment plan (§12.2) with the trust entries it produces. Each links its twin's record by canonical hash: the entry card's `twin_calibration`, the plan's `subject.twin_calibration`. The linked record has the comparison's simulator, and the embodiment of the reference set or the plan subject. A comparison is `uncalibrated` when the link is null or the linked record is `uncalibrated`.
- **Rule.** An `uncalibrated` comparison is marked `uncalibrated`, and its numbers are not reported as a comparison result: not as agreement or disagreement between the twin and the real setup, not as a verdict, and not as evidence about the simulator. Internal diagnostics may show them under the mark. The validator enforces the rule where a record would report a result:
  - **Trust entries** carry `twin_calibration`, equal to their plan's status, or `uncalibrated` without a plan. Under a plan with status `customer_draft` or `customer_final`, an `uncalibrated` entry has verdict `not_yet_calibrated` and so holds no estimate; the report lists the calibration gaps in place of a verdict and does not report the plan's cell labels. Plans with status `illustration` or `internal_dry_run` may carry verdicts under the mark.
  - **Our entries.** An entry card with kind `simulator` and `ours` true needs a `calibrated` record before `frozen_at` is set, since a frozen entry is one whose score we report.
  - **Other entries** (`ours` false) link a twin calibration record when the builder discloses one. They stay ranked, with the status shown beside the score; the scoring package reads the status into each entry's row. A results file may report their scores and verdicts as benchmark comparisons, each labelled with its calibration status and information class, as findings about the published data and never as evidence for our method.
  - **Freeze gate.** The validator enforces the freeze gate on our entries. The scoring package does not read `frozen_at`; it lists our uncalibrated simulator entries without ranking them, so their scores never enter a ranking.

**Example.** The twin calibration record in `spec/examples/` describes an SO-101 twin built only from the released ArmnetBench data. Every item is `inferred` or `missing`, so the record is `uncalibrated`; `twin_gaps` lists 22 gaps, among them no recording session, no joint calibration file, no reference poses, no control settings, no excitation recording, no camera board images, and starting layouts for 0 of 30 episodes. ### 13.4 Open items

1. **Rank comparisons.** Released data without calibration may support ranking and stage-level comparisons better than absolute success-rate matching on hobby arms, but we found no measurement of this. v0 applies the rule to every comparison, ranks included. A rank exemption needs evidence.
2. **Unsourced and provisional tolerances.** Intrinsics reprojection error has none; the fixed-object touch error (10 mm) has no source; the gripper error (5 mm) is a proposed threshold.
3. **Choices in the item list.** Fixed-object masses are optional: fixed objects are static bodies in the twin. The replay check needs a recording not used in the fit: an in-sample error understates the twin's error. The drift limit is SO-101 Bench's reported drift. A record needs at least one recording session, so the drift check cannot pass empty. Wrist cameras use the fixed-camera pose tolerance.
4. **World models.** Entries of kind `world_model` carry no twin calibration in v0. Which of the five items apply to a learned video model is not settled.
5. **Other robots.** The items are written for arms. Mobile bases, legs, hands and tactile sensors need items of their own.
6. **One source for camera data.** §6's `camera.extrinsics_from` names a calibration file, separate from this record's camera entries.

## 14. Versions and compatibility

Status: **draft.** These rules govern `spec/v0.md`. They follow the extension rules of `spec/variance-v0.md` §11.

**Rules.**
- **Every record names the version whose rules it follows** in `spec_version`. A validator accepts every version this section still lists, each under its own rules.
- **A minor version** (`v0.1`, `v0.2`, `v0.3`, …) adds fields, values or record kinds and never changes the type or meaning of an existing field, except as the next rule allows. A field it adds as required is required only in records that carry the new label, so every record valid under an earlier version stays valid under that version's label.
- **A replaced rule in a draft record.** While a record kind's status is draft, a minor version may replace a rule that sets a field from other fields of the same record, such as a verdict rule, in records that carry the new label only. The version adds a required field that names the rule, lists the change and its reason in the table below, and states how records of earlier labels are read. Records of earlier labels keep their rule, so every verdict stays reproducible from the label its record declares. v0.4 uses this rule for the trust entry's verdict (§7).
- **A major version** (`v1`) may change types or meanings. It lists every change and the mapping from the previous version.
- **Records are never relabelled.** A record keeps the label it was written with. A producer that can fill the new fields writes a new record with the new label, or a new export of the same source records; it does not edit stored records.
- **Values added to an existing list** (a checker name, a device) may apply to earlier labels when they only name something that already existed; each such case is stated where the value is defined.
- A record kind that a version does not change keeps its earlier label. v0.1, v0.2 and v0.3 change only the episode record, and v0.4 only the trust entry. So episode records carry v0 to v0.3, trust entries (§7) carry v0 or v0.4, and benchmark records (§11), assessment records (§12) and twin calibration records (§13) keep `spec_version: "v0"`.
- **Clarifications** state what an existing field already meant, where the text left it unstated; they apply to every label and are listed in the table. v0.4 states two: a referent from a third party the vendor commissioned or paid is not independent of the vendor (§7, §12.2), and the floor rule of a cell for trial counts other than 50 (§12.1), which a plan may replace with its own.

**Additions.** Any addition after v0.4, however small, takes a new label under the rules above.

**How v0 trust entries are read.** A trust entry carries v0 or v0.4. No trust entry carries v0.1, v0.2 or v0.3, labels that changed only the episode record, and the validator refuses them on a trust entry. A v0 entry is read under the v0 rule (§7, end):
- Its `agree` says that the bias interval lies inside ±δ and that the upper bound of the scatter interval is at most δ. It does not say that the cells agree within δ: with bias and scatter both near δ, about half of the cells can miss by more than δ under a normal model (at bias 0.24, scatter 0.24 and δ = 0.25, 50% lie outside ±δ). A report that quotes a v0 AGREE says "v0 rule: bias and scatter tested separately; not agreement within δ per cell" and prints the limits of agreement, |bias| + 1.96 × scatter, beside it.
- Its DISAGREE labels keep their v0 meaning: `disagree_scatter` says that the lower end of the scatter interval exceeds δ, where v0.4 asks 1.96 times that lower end to exceed δ, and `disagree_offset` says the bias interval lies outside ±δ with no wide scatter.
- A v0 entry carries no non-FLOOR inputs, so a reader cannot apply the padding check to it, and it never carries `disagree_unresolved`.
- It is never relabelled. A producer that holds the source data writes a new v0.4 entry from them.

**How v0 episode records are read.** A v0 episode record names its checker's definitions but not the release, and names neither its scene generator release nor its inference device. A reader treats those as not stated in the record: they may be recoverable from `versions.git_commit`, and a report that quotes such a record says where the release came from. A v0 record is not a replay record: it carries no trace hash and no device, so a rerun of it is a new trial, compared by outcome.

**How v0.1 episode records are read under v0.2.** A v0.1 record does not say whether it ran in a simulator or which physics options it ran under. A reader treats both as not stated, even where `simulator.physics` names some option fields. A report that needs either value takes it from a new v0.2 export of the source records, when they hold it, and never infers it.

**How v0.1 and v0.2 episode records are read under v0.3.** Their `generator`, when not null, names at least one seed, so it is read as `seedless` false. A v0.1 or v0.2 record with `generator` null is a stored scenario document; a reader never takes it for a seedless generator.

**Validation.** `spec/validate.py` picks the episode schema by `spec_version` (`EPISODE` for v0, `EPISODE_V0_1` for v0.1, `EPISODE_V0_2` for v0.2, `EPISODE_V0_3` for v0.3) and refuses other labels. A v0.1 record carrying a v0.2 field or the v0.2 checker is refused, and a v0.1 record relabelled v0.2 is refused (missing fields). v0.2 records also pass every v0.1 rule. v0.3 records pass every v0.2 rule except the non-empty `generator.seeds`, which a v0.3 record with `generator.seedless` true replaces with the empty map. A v0 record carrying a v0.1 field is refused (unknown field), and a v0 record relabelled v0.1 is refused (missing fields). The self-test rejects one fault per v0.1 rule (including a snapshot hash version outside 1 and 2, given as text, null beside a snapshot hash, or named by a start fork) and accepts a full replay record built in memory from the example, with and without `snapshot_hash_version` 2, and for v0.2 rejects one fault per rule of `simulated`, the option hash and §8.4 and accepts v0.2 exports built in memory from the v0.1 example, and for v0.3 rejects one fault per rule of `seedless` and accepts v0.3 exports built in memory from the v0.1 example, with the example's seeds and as a seedless generator (`python3 -I spec/validate.py`); unit tests: `spec/tests/test_episode_versions.py`, `spec/tests/test_physics_options.py`.

It picks the trust entry schema in the same way (`TRUST_ENTRY` for v0, `TRUST_ENTRY_V0_4` for v0.4) and refuses other labels. A v0 entry carrying a v0.4 field or `disagree_unresolved` is refused, as is a v0 entry relabelled v0.4 (missing fields). The published WidowX example stays v0 and keeps `disagree_scatter`. The self-test accepts a v0.4 export of it built in memory, which keeps `disagree_scatter`: δ_D 0.695 from the entry's own intervals, and δ_A 1.149 from the non-FLOOR intervals that the self-test states. It rejects one fault per v0.4 rule, among them a v0-style AGREE whose upper bound on the limits of agreement exceeds δ, an AGREE that fails the padding check, a cause label the data do not resolve, demonstrated tolerances that differ from the bounds, and wrong possible verdicts without a scatter interval. Unit tests: `spec/tests/test_trust_versions.py`, which also checks the possible verdicts of NOT DETERMINED against a dense grid of scatter intervals that contain the point.
